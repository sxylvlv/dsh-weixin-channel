# 出站媒体实测结论（2026-09-13）

> 这份文档记录的是**只能实测得到、源实现与公开协议都没写**的结论。
> 每一条都附判据，便于日后协议变动时快速判断。

## 一、已验证可用的配方（用户肉眼确认两次）

```js
image_item / file_item / video_item: {
  media: {
    encrypt_query_param: <上传响应头 x-encrypted-param>,   // 长度约 488
    aes_key: base64(32 字符 hex 字符串),                    // 长度 44
    encrypt_type: 1,
  },
  // 图片另带 mid_size: aesEcbPaddedSize(plaintextSize)
}
```

对应实现对 `lib/media.mjs` 的 `uploadLocalFileToWeixin`：
`referenceMode='ack-header'`、`includeEncryptType=true`、`includeFullUrl=false`。

### 上传流程

1. `getUploadUrl({filekey, media_type(1=IMAGE,2=VIDEO,3=FILE,4=VOICE), to_user_id, rawsize, rawfilemd5, filesize, no_need_thumb:true, aeskey:<hex>})`
   - `filesize = ceil((rawsize+1)/16)*16`（PKCS7 补齐后的密文长度）
   - AES key 为随机 16 字节；`filekey` 为随机 16 字节的 hex
2. AES-128-ECB 加密明文 → **POST** 密文到 `upload_full_url`，缺失时回退
   `${cdnBaseUrl}/upload?encrypted_query_param=<upload_param>&filekey=<filekey>`
   （`Content-Type: application/octet-stream`；4xx 立即失败，5xx/网络错误重试 3 次）
3. **下载引用取响应头 `x-encrypted-param`**

## 二、三个反直觉的坑（都踩过）

| # | 现象 | 判据 |
|---|---|---|
| 1 | 用 `getUploadUrl.upload_param` 作 `encrypt_query_param` → **媒体不再投递**；但用它拼 `/download` 我自己 GET 得到 200 | 用户肉眼确认媒体消息不出现 |
| 2 | `aes_key` 用 `base64(16 字节裸密钥)`（24 字符）→ 消息能投递但客户端打不开 | 用户看到占位"图片已过期或被清理" |
| 3 | 加上 `full_url` → 媒体不再投递 | 用户确认只有文字 |

**教训**：判据必须是"**对方是否收到并能打开**"，而不是"我自己能不能 GET 到"。
第 1 条就是因为判据选错，导致我"修好"了一个本来没坏的实现，反而把它搞坏。

## 三、CDN 参数的实际结构

入站报文给出的**已知可用**下载地址：

```
https://novac2c.cdn.weixin.qq.com/c2c/download
  ?encrypted_query_param=<752 字符>
  &taskid=<32 位 hex>
```

- 该 URL 多一个 `taskid`，出站没有来源，**且实测出站加上 `full_url` 会导致不投递**，故出站不提供。
- `upload_param`(936) / 响应头(488) / 入站参数(752) 解码后仍是 base64 串（双层编码的不透明令牌），**看不出内部结构**。
- 入站媒体的 `media` 里**没有** `encrypt_type` 字段；但出站**必须带 `encrypt_type: 1`**（方向不同，不可互推）。

## 四、会话令牌（context_token）

- 每条入站消息携带一个；约 **十余分钟**后失效，此时 `sendmessage` 返回 `ret=-2 errmsg=prepare failed`。
- **过期的令牌比没有令牌更糟**：同一个时间点，带过期令牌发送失败，**完全不带令牌发送却成功**（实测两次）。
  → 因此实现里**不是**"失败后重试"，而是**按年龄判断**：缓存令牌超过 `staleTokenMs`（默认 10 分钟）
  就直接不带令牌发送（`lib/bridge.mjs` 的 `sendWithContextFallback`，r18 起）。
  年龄用凭据文件 mtime 推断——每次 `setContextToken` 都重写该文件。
- 代价：不带令牌的消息可能不并入原会话上下文。
- **正常回复不受影响**（回复时令牌必然是刚刚那条入站带来的、永远新鲜）；**只有主动推送才会撞上**。
- 源实现 `session-guard.ts` 只处理 `-14`（令牌失效 → 暂停 1 小时），**未覆盖 `-2`**。

## 六、关于"调试期的失败"（重要结论）

**出站媒体在正常交互节奏下稳定可用。** 2026-09-13 22:35 一次入站后连发 PDF + ZIP 两个文件，均送达（用户确认）：

```
14:35:07 入站 textLen=31
14:35:25 出站媒体成功 kind=file name=dsh-测试文档.pdf      bytes=2736
14:35:27 出站媒体成功 kind=file name=dsh-测试压缩包.zip    bytes=1424
```

而同一晚 22:23 之后，我用脚本密集直发（十几条媒体、多种参数组合）**全部失败**，表现为两种：

- 返回了 `message_id` 但对方**收不到**
- 紧接着的发送直接 `ret=-2 prepare failed`（**连说明文字都发不出去**）

**结论：协议是正确的，失败是我把通道打限了。**

**教训**：密集调试会污染被测环境——一边测一边加重限流，得到的全是噪声。
**运维要求**：
- 不要在短时间内连发多条媒体；
- 脚本直发测试要限量、留间隔，并优先走"**一次入站 → 一两条出站**"的真实路径；
- 判断"是否修好"必须用**接收端**确认，脚本返回的 `message_id` 只是"服务端受理"，不等于送达。

## 八、两条发送路径的差异（2026-09-13 全程数据复盘）

### 时间线（本地时间）

| 时间 | 路径 | 内容 | 结果 |
|---|---|---|---|
| 21:28 | 脚本 | 图片（坏配方） | 投递但打不开 |
| 21:29 | 脚本 | 文件（坏配方） | 投递但打不开 |
| 21:31 | 脚本 | 图片 + 文件（好配方） | ✅ |
| 21:45–21:57 | 脚本 | 截图 ×4（连试四种字段组合） | ❌ 全灭 |
| 22:07 | 脚本 | 小二维码 | ❌ |
| 22:12 | 脚本 | 二维码 | ✅ |
| 22:13 | **会话内** | 截图 | ✅ |
| 22:22 | 脚本 | docx / xlsx / pptx ×3 | ✅✅✅ |
| 22:23–22:33 | 脚本 | pdf / zip / 小文件 / 改名文件 ×8 | ❌ 全灭 |
| 22:35 | **会话内** | 它自己生成的 pdf + zip | ✅✅ |

### 结论：差异不在"谁发"，而在两个使用条件

**脚本也成功过（22:12、22:22 三次），会话内也失败过。**所以不是"路径"本身的差别，而是两条路径**天然满足的条件不同**：

| 条件 | 会话内（被入站触发） | 主动发（我的脚本） |
|---|---|---|
| **令牌新鲜度** | 必然是**刚刚那条入站**带来的，秒级新鲜 | 用缓存令牌，常已过期（>10 分钟）→ `ret=-2` |
| **发送密度** | 一次 1–2 条，间隔由真实对话决定（分钟级） | 我为排查会**秒级连发 5–10 条** |
| 触发来源 | 用户请求 → 正常的"回复"流 | 无入站的**主动推送** |

**失败全部集中在"加密集发送"的时段**（21:45–21:57、22:23–22:33），而单次、稀疏的发送（含脚本）都成功。
→ 主因是**发送密度触发的限流**，其次才是令牌过期。

### 据此做的插件优化（r18 / r19）

| 优化 | 位置 | 作用 |
|---|---|---|
| 令牌过期即**不带令牌**发（而非撞失败再重试） | `lib/outbound.mjs` `beforeSend` | 过期令牌会被拒、不带令牌反而可发（实测） |
| **最小发送间隔** 1.5s | 同上 | 防止突发送 |
| **断路器**：连续 3 次可恢复失败 → 冷却 5 分钟 | 同上 | 不再猛撞被限流的通道 |
| **发送台账** `media-log.jsonl` | 同上 | 记录每次出站的时间/类型/字节/令牌年龄/结果 → 事后一次对比即可定位 |
| 所有出站统一走守卫 | `lib/bridge.mjs` | 会话内的文字与媒体都过同一层 |

**仍是欠的**：`tools/*.mjs` 这些**调试脚本绕过守卫**（今晚的密集发送就是它们干的）。
建议后续把它们也接到 `lib/outbound.mjs`，或至少加"每次运行前提示：直发测试会污染限流状态"。

### 判据（写死，别再犯）

1. **`message_id` 只代表服务端受理，不代表送达** —— 判断成败必须用接收端确认。
2. **不要用脚本密集直发来验证** —— 会污染被测环境；优先走"一次入站 → 一两条出站"的真实路径。
3. **异常先停手等冷却**，不要在同一时段连试多种组合。
